# MT DevOps Framework Companion

A thin VS Code companion for the [MT DevOps Framework](https://github.com/MatStacey/mt-devops-framework) -- gives command-palette access to its full `mt-` command catalog without needing to remember command names or drop into `mt-search -i`/`mt-fzf` in a terminal.

This is a thin client: it never reimplements framework logic. Every command it runs is sent straight to a real, framework-loaded shell, so behavior always matches what you'd get typing the command yourself.

## Features

* **`MT DevOps: Run Command...`** -- fuzzy-searches the framework's entire command catalog (aliases and functions, generated from the framework's own `COMMANDS.md`) and runs your selection in a reused "MT DevOps" integrated terminal.
* **`MT DevOps: Show Status Dashboard`** -- shortcut for `mt-status`, the framework's health-check dashboard.
* **`MT DevOps: Check for Extension Updates`** -- checks this pack's latest GitHub release against every installed extension from it (mt-devops-companion, and either extension pack manifest, if installed) and offers to download + install (via VS Code's own `workbench.extensions.installExtension`, no `code` CLI dependency) whichever are outdated. Also runs automatically once every 24 hours on startup (toggle: `mtDevops.checkForUpdatesOnStartup`) -- since this pack isn't on the Marketplace, VS Code's own auto-update never covers it.
* **`MT DevOps: Generate/Update README (AI)`** / **`... .gitignore (AI)`** -- also available as buttons on a repo's report page (see Repo Hub below), or right-click a folder in the Explorer. Runs `mt-ai-readme`/`mt-ai-gitignore --update --json`: if the file doesn't exist yet, it's generated directly; if it does, the framework regenerates it into a pending file (`.git/mt-ai-pending-...`, never overwriting anything itself) and this shows a native side-by-side diff, then asks **Apply** or **Discard** before committing to the change. From the bare command palette (no Explorer/editor context to infer a repo from), you're prompted to pick from whichever repos are currently open in the workspace.
* **`MT DevOps: Explain Code (AI)`** -- available from the command palette, an editor right-click, or an Explorer file right-click. Explains a highlighted selection, an unsaved buffer, a saved file, or an Explorer-selected file via `ai-explain -f <file>` (a selection/unsaved buffer is written to a temp file first, since `ai-explain` reads real files, not inline text).
* **`MT DevOps: Cleanup LLM Exports`** -- runs `mt-export-cleanup -i` in the terminal (its own interactive flow handles the rest). Not repo-scoped -- it clears `mt-export`'s own output directory wherever `config.yaml` points it -- so this is command-palette only rather than a Repo Hub action.
* **`MT DevOps: Search Repos`** -- prompts for a term, then searches the already-indexed `.vcs_hub.json` cache (name, description, category, stack, and GCP detection -- the bare term "gcp" matches every repo with any GCP usage detected at all, a term like "cloud run" or "bigquery" matches only repos referencing that specific product) via `mt-hub --search --json`, and opens the picked match's report. Only ever looks at cached metadata -- a repo never indexed won't match anything, same as it not appearing in the Repo Hub tree at all.
* **MT DevOps activity bar view**, with twelve panels:
  * **Jobs** -- the background job registry (`mt-jobs`), live-updated; click a finished job to open its log. Right-click a job to **Re-run**, **Stop** (while running), or **Remove from History**; the view's title bar has a **Clear Completed/Failed** button (`mt-jobs --clean`) for bulk cleanup. These shell out to `mt-jobs --restart/--stop/--remove <job_id>`, the same non-interactive per-job actions its own interactive picker uses.
  * **Repo Hub** -- two control rows pinned above everything else: a **Background Indexing** checkbox (ticked, every `mt-hub --index` call this view builds runs with `-b`/`--background`, detaching into a Jobs-panel-tracked background job instead of streaming in the shared terminal -- useful for a bulk run you don't want to sit and watch) and an **AI Provider Override** row (click for a quick pick between `gemini`/`claude`/`claude-code`/`local`, or "Default" for none -- the GUI equivalent of `mt-hub`'s own `-p`/`--provider`, e.g. to save Claude usage by indexing with Gemini instead without touching `ai.default_provider` in config.yaml). Both are session-persisted (VS Code's `globalState`, same mechanism as Favorites) and apply to every index/update action below, everywhere in the extension it's triggered from -- context menus, title-bar buttons, the Explorer counterparts, and the Repo Report's own "Update Missing Index" button. Then a dashboard summary line ("N indexed repos · N need indexing · N dirty" -- all from data already cached or, for "dirty," a cheap check bounded to whatever's actually open, never the full repo list), a **Favorites** section (right-click any repo for **Toggle Favorite**; persisted locally, not a real `mt-hub` grouping -- appears anywhere the repo does, star-prefixed), then `mt-hub`'s own AI/heuristic dashboard of every repo under `VCS_ROOT`, grouped by its top-level subfolder (e.g. Personal/Work), plus an **Open in VS Code** section listing whichever of the current workspace's folders are actually git repos (checks for `.git`, so a plain non-repo folder added to the workspace is excluded) -- refreshes automatically when a folder is added to or removed from the workspace, and its entries get a small dot + tinted icon when they have uncommitted changes. Right-click it for **Index All Open Repos** / **Update Missing Indexes in Open Repos** -- since it's not a real `mt-hub` `-t`/`--type` folder, these chain one `-r <name>` invocation per repo rather than a single filtered call, unlike the per-category actions below. Click a repo to open a **report**: its local path (click to open a new terminal there) and remote URL (click to open it in the browser) underneath the title, description, category, stack, build/CI/CD/testing detection, last-indexed time, an **Environments** section (AI-inferred deploy/runtime environments -- e.g. a Compose service, k8s namespace, or CI deploy stage -- shown as colour-coded dev/staging/prod/test pills; omitted for repos with none), a **Google Cloud Platform** section (heuristic, not AI -- a "google"/"google-beta" Terraform provider block or any `google_*` resource type, falling back to app.yaml/cloudbuild.yaml/registry references when there's no Terraform at all; shown as pills naming the actual GCP products referenced, e.g. Cloud Run/GKE/BigQuery, or a bare "GCP" pill when detected without any specific product; omitted entirely for non-GCP repos), a **GitHub** section (open PR count and the default branch's latest CI run, via `gh`; GitHub remotes only, silently omitted if `gh` isn't installed/authenticated or the remote is something else), recent commits (hashes link to the commit on GitHub/Bitbucket when the repo has a recognized remote), remote branches newest-first (paginated 10 at a time) with a **Fetch** button for any not yet local, an **Open in Browser** button, an **Update (Pull ...)** button that appears only when the local branch is behind its upstream, an **Update Missing Index** button, **Generate/Update README** and **Generate/Update .gitignore** buttons (see below), a **Check Dependencies** button (runs `mt-audit-deps --json` on demand -- npm audit for a `package.json`, pip-audit for a Python project, otherwise reports the manifest as unsupported; not run automatically since a real audit hits a registry/database and can take several seconds), a **View in Docker Panel** / **View in Helm Panel** button when the repo has a Compose file / Helm chart, a stale-README warning banner (git's own commit history, not filesystem mtimes, compares the README's last commit against the repo's latest -- a fresh clone stamps every file's mtime as checkout time, which would make an mtime-based check meaningless) above the rendered README, and the README itself at the bottom. Right-click a repo for **Open in VS Code**, **Index This Repo** (force a fresh reindex), **Update Missing Index** (only if its entry has a gap -- see `mt-hub`'s own `-u`/`--update`), **Pull if Behind** (`mt-bulk-update`'s pull-only, fast-forward-only update -- never pushes, never force-merges), **Push All Changes (AI)** (`git-ai-push-all`, confirms first since it publishes to the remote), **Export for LLM** (`mt-export -i`, its own interactive flow runs in the terminal), and **Export Wizard (GUI)** (see below). The same Index/Update/Pull actions are available per-category and per-open-repo, plus **Index All Repos** / **Update Missing Indexes** / **Pull All Repos (if Behind)** / **Create LLM Export** / **View Exports** in the view's title bar (the bulk index and pull actions both confirm first). **Create LLM Export** isn't repo-scoped by construction (there's no right-clicked item at a title bar), so it picks a target the same way the AI generate buttons' command-palette form does -- the one open repo if there's exactly one, otherwise a quick pick -- then runs `mt-export -i` there; **View Exports** opens the real `EXPORT_DIR` (`paths.export_dir`) in the OS file explorer/Finder. `mt-hub --index` itself now warns (and asks for confirmation, in a real terminal) before actually calling AI on more than a configurable number of repos in one run -- see the Settings panel's `ai.enable_bulk_index_warning`/`ai.bulk_index_warning_threshold`.
  * **Export Wizard** -- a GUI front end for `mt-export`'s own `-s`/`-e`/`-x`/`-z` flags, opened via a repo's **Export Wizard (GUI)** context-menu entry (or the command palette/Explorer, which resolve a target the same way the other bare-invokable commands do). Three control rows at the top -- **Schema** (quick pick, reading the real schema files under `~/.bash.d/config/export/schemas`), **Extension Exclusions** (a free-text input box, comma-separated, e.g. `log,tmp,map`), **Output Format** (click to toggle TXT/ZIP) -- followed by an Explorer-like tree of the repo's files and folders with a checkbox on every entry: ticking one marks it for exclusion (the reverse of a normal picker, since the common case is excluding a handful of noisy paths, not hand-picking everything to include), and ticking a folder excludes everything under it via the same path-matching `mt-export -e` already does -- there's no need to also tick its children individually, since matching happens on the real export regardless of what's shown ticked in the tree. Directories `mt-export` already excludes unconditionally (`llm_exports.dir_ignore_glob` -- `node_modules`, `.git`, `.venv`, etc.) are hidden from the tree entirely rather than shown as no-op checkboxes. A **Show Export Plan** action at the bottom (also a title-bar button) runs `mt-export --plan --json` with everything the wizard currently has configured and opens an **Export Plan** page -- target/export dir, output filename, schema, format, total files, estimated size, and extensions -- with a **Proceed with Export** button (runs the exact same command for real, then offers **Reveal in Explorer** for the finished file) and a **Back to Wizard** button to make further changes first.
  * **Secrets** -- the framework's full supported-secrets registry (Gemini, Claude, Bitbucket, Docker Hub), configured or not, with status (created/expiry/last-used dates, colour-coded expired/expiring/active) -- never reads the actual secret values. Right-click any secret for **Add / Update Secret** (opens a terminal running the real `mt-add-*-key`/`mt-add-*-secret` command, since it needs to prompt for the value); a configured secret also gets **Delete Secret** (confirms first, then `mt-secrets --delete`, no undo).
  * **Settings** -- three top-level groups, all backed by the same `config.yaml` (no separate settings store): **Framework** is the full schema (core/paths/ai/git/llm_exports/docker/server/cicd/minikube/display) grouped into collapsible sections exactly as before; **MT Hub** and **MT Export** are curated shortcuts surfacing just the subset of that same config that backs `mt-hub`/`mt-export`'s own CLI defaults -- e.g. MT Hub's `ai.default_provider` (the same override `mt-hub --index -p <provider>` takes on the CLI, settable here as a persistent default) and `ai.enable_bulk_index_warning`/`ai.bulk_index_warning_threshold`; MT Export's `paths.export_dir`, retention (`llm_exports.enable_auto_cleanup`/`auto_cleanup_days`), file-count thresholds, and blocklist/ignore-glob. (Schema/exclude/zip/quiet aren't duplicated here since `mt-export -i`'s own interactive flow already prompts for those per run.) Every entry, wherever it appears, edits the identical dotPath -- click (or right-click "Edit Setting") any value to change it, a boolean gets a true/false picker, everything else a pre-filled input box -- written back via `config_manager.py update <section> <key> <value>`, the same path every `mt-set-*`/`mt-toggle-*` command uses, so validation, `.env.cache` invalidation, and file permissions all stay in one place. Never shows secrets.sh contents; those live in the Secrets panel above.
  * **Logs** -- the last 300 entries from `framework.log` (`mt-log`'s own centralized logging), newest first, colour-coded by level (INFO/SUCCESS/WARN/ERROR), reading the file directly rather than shelling out since it live-updates on nearly every framework command. Title bar buttons: **Clear Logs** (`mt-logs --clear`), **Open Log File** (raw file in the editor), and **Tail in Terminal** (`mt-logs --follow`, for watching many fast-scrolling entries live rather than the fixed last-300 list).
  * **Status** -- `mt-status`, structured into Framework / **Extension** / Sync Repo / Docker / Updates. The Extension section shows this extension's own installed version (mirroring the Framework section's version row); the Updates section gets a matching "Extension" row (up to date / a newer version available), checked against the same GitHub release `MT DevOps: Check for Extension Updates` uses.
  * **Doctor** -- `mt-doctor`'s checks, grouped by section with pass/warn/fail icons.
  * **Docker** -- running/stopped containers (`docker-ls`). Right-click a container for **Start**/**Stop**/**Restart**, **Tail Logs**, or **Open Shell (SSH)** (`docker exec`) -- these call the framework's own `__docker_container_*` helpers (the same ones `docker-containers`' interactive console uses per-container), so messaging matches running them by hand. Logs and shell open in the integrated terminal since both need a real attached TTY. The title bar's **Toggle Group by Repository** button groups containers by their Compose project's working directory (the repo a `docker-compose.yml` lives in) instead of the flat list -- containers with no Compose label (a plain `docker run`) fall into an "Ungrouped" bucket.
  * **Kubernetes** -- active context plus every pod in the current namespace (`k8s-status`/`k8s-pods`).
  * **Helm** -- current context, Helm version, release/repo counts (`helm-status`), and every release across all namespaces (`helm-list`), status-icon coded (deployed/failed/pending/uninstalling). Right-click a release for **Uninstall Release** (confirms first, then `helm-uninstall <release> -n <namespace>` in a visible terminal -- the framework's own `__k8s_confirm_destructive` guard still runs there, since it does real prod-context/namespace detection a dialog can't).
  * **Minikube** -- the default profile's status (`mk-status`): driver, host, kubelet, and apiserver state. Shows an informational (not error) row when no cluster is running yet, since that's an expected state, not a failure.
  * **History** -- the last 50 entries from `mt-history` (framework commands found in shell history), newest-relevant-first. Right-click an entry for **Re-run** -- sends that exact command text straight to the terminal, the same command the extension already has from `mt-history --json`, no extra framework flag needed.

  Jobs, Repo Hub, Secrets, Settings, and Logs update live as their underlying files change -- including after a sidebar action like re-running a job, indexing a repo, or editing a setting, since those rewrite the same underlying files. Status, Doctor, Docker, Kubernetes, Helm, Minikube, and History are refreshed on demand (the refresh button in each view's title bar), since each refresh is a real shell invocation rather than a file read.
* **`@mtdevops` chat participant** -- ask it anything (`ai`), or use its slash commands: `/explain <command>` (`ai-explain`) and `/iam` (`tf-ai-iam`, analyzes the first open workspace folder). When a reply is code that `ai` saved to a file (rather than a plain chat answer), the participant reads that file back and shows it inline in the chat too, with an "Open Generated File" button -- the file is still the source of truth (this is read-back, not a reimplementation of `ai`'s own save/categorize logic).
* **Explorer right-click "MT DevOps: Copy for LLM"** -- runs `mt-copy` on the selected file or folder, copying it (with headers) to your clipboard.
* **Explorer right-click "MT DevOps: Show Repo Report" / "Index Repo (force reindex)" / "Update Repo Index (fill gaps only)"** -- the Repo Hub tree's own report/index/update actions, reachable from wherever a repo is already open in the editor. Only shown for folders (`explorerResourceIsFolder`), and further guarded at runtime against right-clicking a folder that isn't actually the root of a git repository (checks for `.git`, matching mt-hub's own repo discovery -- a worktree's `.git` file counts too) -- these match by exact basename against `mt-hub`'s own `-r`/`--repo` filter, so a non-root folder would otherwise silently target the wrong repo, or none.

## Requirements

The [MT DevOps Framework](https://github.com/MatStacey/mt-devops-framework) must be installed and loaded into your interactive shell (`~/.bash.d`). Commands are run via VS Code's integrated terminal, which sources your shell profile the same way a regular terminal tab would. The tree views shell out to a genuinely interactive `bash -ic` for the same reason (a plain `bash -c`/`bash -lc` never loads the framework at all, since `~/.bashrc` itself is guarded to only run interactively).

## Keeping the command catalog current

The catalog in `data/commands.json` is generated from the framework repo's own `COMMANDS.md`, not hand-maintained. If you have both repos checked out as sibling directories (the default `~/vcs/personal/` layout), regenerate it with:

```bash
npm run sync-commands
```

Override the source path with the `MT_COMMANDS_MD` environment variable if your checkout layout differs.

## 🚀 How to Install

1. Download the latest `.vsix` release artifact from this repository's **Releases** page.
2. Open Visual Studio Code.
3. Navigate to the **Extensions** view (`Ctrl+Shift+X` or `Cmd+Shift+X`).
4. Click the `...` (Views and More Actions) menu in the top right of the Extensions panel.
5. Select **Install from VSIX...**
6. Locate and select the downloaded `.vsix` file.
7. Reload VS Code when prompted.
